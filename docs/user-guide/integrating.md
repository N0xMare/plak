# Integrating with plakd

Choose the boundary that fits your application. There is one agent runtime,
whether you embed it or drive the product out of process.

The host supplies account and model catalog facts and settings metadata.
Clients present those facts and own their input, navigation and rendering.
The repository ships no application client or client SDK.

| Surface | Use it for |
| --- | --- |
| In-process `plakous` | A Rust application that owns construction, tools, credentials and persistence. Start with [Embedding](embedding.md). |
| `plakd agent` | Existing single-session JSONL v1 clients; retained byte-identical until removal. |
| `plakd host connect --stdio` | A transparent child-process transport to the host's wire protocol; diagnostics stay on stderr. |
| `plakd host` | A long-lived session directory over a private same-user Unix socket, `plakd host connect --stdio`, or the authenticated WebSocket endpoint. |
| `plakd run` | Non-interactive jobs: prompt in, final answer on stdout, progress on stderr, and a process exit status. |
| `plakd runner` | Paired execution placement for an existing host, not a frontend API or another agent loop. |

The [CLI reference](cli.md) covers flags. The normative contracts are
[wire v2](../spec/02-plak-product.md#44-wire-v2),
[host lifecycle](../spec/02-plak-product.md#46-plakd-host) and
[exit classes](../spec/02-plak-product.md#33-exit-codes). The host and runner
protocols are distinct. New framed-wire integrations use the supported host
socket or stdio bridge. `plakd agent --wire v2` is a hidden, unsupported
single-session entrypoint, not the supported stdio integration boundary.

## Schema and exact versions

```sh
plakd wire schema > wire-schema.json
plakd host connect --stdio
```

Start `plakd host` separately, then spawn the stdio bridge from your client and
read and write its pipes concurrently. The bridge discovers the current host;
starting a missing host requires explicit `--auto-start`. Bare `plakd` prints
help and starts no host or session. The hidden `agent --wire v2` form is not a
supported application-client entrypoint.

`plakd wire schema` is supported in ordinary release builds. Release assets
include `plakd-<version>-<triple>-wire-schema.json`, generated by that target's
binary and covered by `SHA256SUMS` and build provenance. Prefer the schema
printed by the actual binary when integrating a source build.

The `v2` grammar currently carries `proto: 12`. Versions match exactly, with no
negotiation or downgrade. Check `wire_version` and `binary_id` in the schema;
on a mismatch, update the client for the binary you intend to use rather than
retrying another version. A socket, the stdio bridge, and WebSocket all carry
the same JSON frames. WebSocket authentication, origin checks and message
boundaries are described in spec 02. The example below uses the stdio bridge
to a same-user host, not a web endpoint.

## Hello, find a session, attach

Start `plakd host` in a separate process. A directory host's welcome names no
single session. Use the directory to find an existing session or create one
through `new_session` after checking the host's runner, workspace and profile
options in the schema. Creating a session is an explicit operation, not a
side effect of connecting. Supply a UUID `request_id`, the selected `runner`
object and absolute `workspace` in the request's `new_session` operation.
Reuse that UUID if its answer is lost; do not create another session to resolve
an unknown outcome. The `created` answer supplies the node for an immediate
attach. Directory reads reflect a background projection: a list immediately
after creation may not include the row yet. Watch the directory if you need
its published row.

Each frame is one newline-terminated JSON object on a socket or stdio stream.
Send hello first:

```json
{"frame":"hello","proto":12,"binary_id":"python-example","caps":[]}
```

The host replies `welcome` with its matching `proto`, binary id, `state_key`, generation,
capabilities and principal-specific extension. Generations are wall-clock-based
identities, not monotonic counters: compare for inequality only, never ordering.
List sessions:

```json
{"frame":"request","id":1,"op":{"op":"list_sessions","include_archived":false}}
```

The response with `id: 1` has `outcome.ok.answer: "sessions"` and `rows`.
Find the desired session and copy its `node` address **as returned**; a root's
agent id is not necessarily the literal `root`. Attach that address:

```json
{"frame":"request","id":2,"op":{"op":"attach","node":{"tree_id":"<tree-id>","agent_id":"<root-agent-id>"}}}
```

The response with `id: 2` answers `attached` and names an attachment. Snapshot
pages and events follow; a snapshot's `last: true` completes that revision.
Keep request ids distinct and correlate responses by id while reading other
frames. Send `{"frame":"bye"}` before closing. Reconnect means a new attach,
not replaying requests or inferring lost model/tool outcomes.

An admitted planned restart or upgrade may send `host_lifecycle` before closing.
Its phase is `draining`, `restarting`, `stopping`, or `running` (an aborted
drain), with reason `paired_upgrade`, `cross_key_upgrade`, or `shutdown`.
`cross_key_upgrade` remains in the wire format but is no longer emitted.
Optional `target` names the binary id and state key; optional
`retry_after_ms` is at most 30000. Treat these as advisory only: reconnect and
attach afresh, and never replay a prompt because of a notice or a lost reply.
Notices can be missed or repeated. A state-key cut is offline: reconnect to
the new host and attach using the IDs printed by import.

During an admission pause, the host drops non-request payload frames such as
blobs without acknowledging them. Hold unsent drafts and their blobs in the
client. A Welcome from the expected binary and a different host generation
confirms the handoff, not that owed sessions have loaded. Retry an attach or
prompt that explicitly returns `backpressure` until the session is ready.
For a refused prompt, keep its submission ID and resend its blobs with the
retry; a missing reply is not a refusal and does not authorize replay.

The stdio bridge reads one bounded Hello first. With a matching version it can
instead print one `{"frame":"refused","kind":"bridge_unavailable","reason":"absent","retry_after_ms":500}`
and exit 1. Other reasons are
`starting`, `stopping`, `incompatible_state`, `verification_failed`, and
`start_refused`; clients
must not parse stderr to classify them. Absence, starting and stopping are
retryable; incompatible state, verification failure and start refusal need operator repair.
`start_refused` means local startup policy requires an explicit operator action
(for example, a remote shell or an installed user unit), and carries no retry hint.
An optional hint is at most 30000 ms. A connected bridge forwards that Hello
unchanged; wire 10 receives only `version_mismatch`, even with no host.

To build a usable client, implement snapshot assembly, sequence/gap handling,
scope resync, bounded blob assembly and the typed session intents described by
the schema. Keep submission identities stable across unknown outcomes; do not
turn reconnect into prompt or effect replay. Render catalogs, settings metadata
and capability refusals supplied by the host instead of reconstructing product
policy locally. Credential and confirmed settings operations remain host-owned.

Rust integrators can inspect the neutral frame, intent and view types in
[`plakous-host-protocol`](../../crates/hosting/host-protocol/src/lib.rs) and the
product extensions in
[`plakd-wire-types`](../../crates/hosting/plakd-wire-types/src/lib.rs). These are
published-internal packages, not a supported client SDK. Other languages can
generate or validate their own types from `plakd wire schema`. The offline
[`wire_client` contracts](../../bin/plakd/tests/integration/wire_client.rs)
exercise the transport without providing an application client.

## A bounded CI job

Supply an API credential through the CI system's secret environment, not an
argument or a checked-in file. Choose an exact model id available to that
account; `PLAK_MODEL` below is an example caller-owned variable.

```sh
: "${OPENAI_API_KEY:?set this through the CI secret environment}"
: "${PLAK_MODEL:?set an exact OpenAI API model id}"
export PLAK_HOME="$(mktemp -d)"
trap 'rm -rf -- "$PLAK_HOME"' EXIT
if plakd run --account openai --model "$PLAK_MODEL" --effort low \
    --max-turns 5 --timeout 300 -- 'Run the tests and explain any failures.' > answer.txt; then
  status=0
else
  status=$?
fi
case "$status" in
  0) echo 'completed' ;;
  2) echo 'invalid invocation or selection' >&2 ;;
  3) echo 'credential/admission failure' >&2 ;;
  4|130) echo 'interrupted or shutdown did not join' >&2 ;;
  5) echo 'agent/product failure or recovery required' >&2 ;;
  6) echo 'turn/time budget reached' >&2 ;;
  7) echo 'session held by another live process' >&2 ;;
  *) echo 'configuration or other failure' >&2 ;;
esac
exit "$status"
```

Use `--effort` only if the chosen model requires it. `run` has full host tool
authority and no approval gates; use a disposable CI workspace with the
authority you intend to grant it. Its success means the agent completed, not
that a separate test command necessarily passed; enforce required checks in
your surrounding job. See the CLI reference for output and continuation rules.

## Service setup

[Host service setup](host-service.md) covers Linux systemd user units and
macOS per-user LaunchAgents. `plakd host install` writes both the host and
credential gateway service files, sets the default Unix gateway address, and
prints platform-specific start, log and removal commands; it never enables
or starts the service. On Linux the printed steps also cover optional lingering.
On macOS follow the printed `launchctl` steps, not the Linux systemd commands.
